# Phase 3 -- Leakage-Safe Preprocessing Report

Generated by `src/preprocessing.py`. The raw CSV is treated as immutable; nothing in this phase modifies it.

All preprocessing parameters are intended to be learned only from training folds.

---

## Feature schema

The modeling feature set is deterministic and ordered as follows:

1. `Age` (numeric)
2. `Gender` (categorical)
3. `Total x` (numeric)
4. `Totaly` (numeric)
5. `TUG` (numeric)

This exact order is preserved across training, validation, testing, and external validation.

Do not rely on arbitrary dataframe column order. The feature order is explicitly defined in `configs/phase3_config.json`.

## Target handling

- **Target column:** `HighFallRisk`
- The target is never included in the feature matrix X.
- Target values are validated for binary values (0/1) and absence of missing values.
- The target is not transformed, rebalanced, or redefined.
- Class counts: 0=44 (Controls), 1=33 (Fallers)
- `HighFallRisk` is treated as the cohort label pending source verification (see Phase 2 unresolved issues).

## Identifier handling

- **Identifier column:** `Participant_ID`
- The identifier is excluded from the feature matrix X.
- Participant IDs are preserved in metadata so predictions/results can be traced back to participants without using the ID as a predictor.
- Identifiers are never used as predictors.

## Missing-value strategy

- **Strategy:** Median imputation for numeric candidate predictors.
- The imputer is fit only on training data.
- The fitted median is then used to transform validation/test data.
- No information from validation or test data influences the fitted median.
- No missingness indicator features are added.
- **Learned medians (from all available data, for documentation only):**
  - Age: 78.45
  - Total x: 0.9667
  - Totaly: 106.595
  - TUG: 10.78

### Leakage rule compliance

The imputer MUST be fitted only on the training data when used inside cross-validation. The architecture exposes `fit_preprocessor_on_training()` and `transform_with_fitted_preprocessor()` to enforce this separation explicitly. In Phase 4, the preprocessor will be fit inside each training fold of the cross-validation procedure.

## Scaling strategy

- **Scaler:** RobustScaler (median-centering, IQR scaling).
- The scaler is fit only on training data.
- The fitted scaling parameters are reused for validation/test data.
- **Scale parameters (learned from training data):**
  - Scale (IQR): Age=5.99, Total x=0.033, Totaly=89.62, TUG=3.87
  - Center (median): Age=78.45, Total x=0.9667, Totaly=106.595, TUG=10.78

RobustScaler is preferred over StandardScaler because the data contains potential outliers (Phase 2 IQR analysis) and the sample is small.

## Categorical handling

- **Categorical features:** `Gender`
- Gender is preserved with its original documented coding (0/1).
- No gender coding direction is assumed or reversed.
- Categorical features are passed through unchanged (no encoding applied) since Gender is already binary.
- The coding direction (which value corresponds to which sex) remains an unresolved scientific issue pending source documentation.

If a future model requires explicit encoding, it must be explicit, reproducible, and documented.

## Outlier policy

- **No outlier removal.**
- No observations are deleted, winsorized, clipped, or replaced based on IQR.
- Phase 2 IQR analysis is descriptive; outliers remain in the modeling data.
- Outlier handling, if needed, belongs to a future scientifically justified sensitivity analysis.
- All 77 participants are retained regardless of statistical extremeness.

## Feature-selection policy

- **No feature selection.**
- All five candidate features (Age, Gender, Total x, Totaly, TUG) are retained.
- Phase 2 statistical significance does NOT determine which features enter ML.
- No p-value-based screening, univariate screening, RFE, LASSO-based selection, correlation-based deletion, or VIF-based deletion.
- The feature set is predefined by the scientific specification, not by data-driven selection.

## SMOTE policy

- **SMOTE is disabled.**
- No resampling is performed.
- Class imbalance (44 controls, 33 fallers) is handled by class weighting in future model phases.
- Any resampling would occur inside training folds only.
- The class ratio (~1.33:1) is relatively modest and class weighting is preferred over oversampling.

## Leakage prevention

All preprocessing parameters are learned ONLY from training folds:

- **Imputer:** Fitted on training fold data only. The median used to impute missing values comes exclusively from the training fold.
- **RobustScaler:** Fitted on training fold data only. The median and IQR used for scaling come exclusively from the training fold.
- **`Participant_ID`** excluded from X.
- **`HighFallRisk`** excluded from X (it is the target).
- **`سابفه سقوط`** (fall-history) remains excluded pending leakage verification.
- All 22 completely empty columns are excluded from X.
- No temporal leakage can be ruled out from the CSV alone.
- The preprocessor is designed to be fit inside each cross-validation fold, never on the full dataset.

### Explicit leakage test

An explicit test demonstrates that validation data with deliberately extreme values (Age=150-170, TUG=50-70) cannot influence the imputation medians or scaling parameters computed from training data (Age=70-74, TUG=8-10). After transforming the validation data, the training-derived parameters remain unchanged.

## Cross-validation compatibility

- The preprocessor is designed to be fit inside each cross-validation fold.
- `build_preprocessor()` returns a sklearn `ColumnTransformer`.
- `fit_preprocessor_on_training()` and `transform_with_fitted_preprocessor()` provide explicit fold-safe API.
- Phase 4 will use this preprocessor inside nested stratified K-fold CV.
- The preprocessor is a stateless transformer after fitting; it only applies learned parameters.

## External-validation compatibility

- The preprocessor is designed to be frozen after fitting on development/training data.
- External validation data is transformed using the frozen preprocessor.
- External data NEVER refits imputation parameters, scaling parameters, or feature selection.
- The feature schema is deterministic and consistent across all data splits.
- If external validation requires a different preprocessing approach, the frozen parameters from development data must be used.

## Tests

Phase 3 tests are in `tests/test_phase3.py` and cover (27 tests, all passing):

1. **Feature schema** - exact order and content verified
2. **Target exclusion** - `HighFallRisk` not in X, binary values, no missing
3. **Identifier exclusion** - `Participant_ID` not in X
4. **Empty column exclusion** - 22 empty columns cannot enter X
5. **Imputer behavior** - median computed from training data only
6. **Leakage-safe transform** - validation does not refit or alter parameters
7. **Scaler behavior** - fitted on training, reused for validation
8. **Raw data immutability** - byte-for-byte unchanged
9. **Determinism** - repeated construction produces same parameters
10. **API verification** - ColumnTransformer type, output shape, passthrough
11. **Output files** - JSON, schema, and report generated

## Unresolved scientific issues

1. **Gender coding direction** - which value (0 or 1) corresponds to which sex is not documented in the source.
2. **`HighFallRisk` semantics** - whether this represents a clinically validated high-fall-risk diagnosis or the original LTMM cohort label remains unverified.
3. **`سابفه سقوط` leakage** - whether fall history was part of label assignment is unverified.
4. **`Total x` and `Totaly` semantics** - whether they equal normalized MMSE and PASE respectively is unverified.
5. **Age precision** - Age values carry many significant digits; the generating calculation is undocumented.
